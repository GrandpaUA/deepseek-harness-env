# Протокол делегації: голова → жори (DSH-версія, v3)

Порт діючого протоколу з `tools/hands_strategy.md` (розд. 8) проєкту
youtube-translator. Виконавців називаємо "жори" (чол. рід: один жора, два
жори, багато жор). У DSH руки = `subagent` / `workflow agent()` / `ralph`;
обгортка hands.sh більше не потрібна — рантайм DSH сам дає PID-лок,
таймаути, нотифікації і структуровані звіти.

## 1. Класифікація: кому що віддавати

| Тип задачі | Виконавець |
|---|---|
| Фікс/фіча 30–60 хв, файли відомі, критерій = тести | жора (`subagent`, background) |
| Паралельні незалежні задачі (РІЗНІ файли) | 2–3 жори одночасно |
| Фан-аут по багатьох штуках (аудит, міграція, мультикутний ресерч) | `workflow` (pipeline/parallel) |
| Чекаюча задача (довгий білд, зовнішня job'а) | `pwsh run_in_background` + `job_output`, НЕ жора — принцип 2: очікування спалює бюджет |
| Ресерч з вебом | голова або жора з явною вимогою evidence (URL-и); у DSH web_search нативний, але вердикт "з пам'яті з виглядом повноцінного" — заборонений (принцип 5) |
| Архітектура, рев'ю, рішення, точкові правки 1–2 рядки | голова |
| Довга ітерація до цілі з чистим листом | `ralph` (fresh-agent раунди) |

**Правило максимальної делегації:** все, що можна специфікувати, — віддавати
рукам. Голова сама робить лише неделеговане: рішення, верифікація, точкові
правки. Але делегація = ПОВНЕ ТЗ (нижче), інакше це не делегація, а лотерея.

## 2. Шаблон ТЗ (обов'язковий для жори)

Жора не бачить твоєї розмови — усе контекстне вкладається в ТЗ. Виняток:
`subagent_fork` наслідує розмову — тоді ТЗ лише дельтою ("що нового").

```markdown
# Задача: <одне речення — що і навіщо>
## Контекст
<причина, інцидент, рішення голови — те, чого нема в AGENTS.md>
## Файли в scope
- path/file1.py — що саме змінити
## Що НЕ чіпати
- <конкретика: тести поза scope, промпти, числа конфігів...>
## Вимоги (тестовані)
- WHEN <умова> THE SYSTEM SHALL <поведінка>
## Критерії приймання
- `pytest tests/test_x.py` зелений — покажи вивід (КОНКРЕТНІ тести, не голий
  pytest: у сьютах бувають інтеграційні тести, що ходять у платні API)
## Якщо задача нереалізована або вимоги суперечливі
- ЗУПИНИСЬ і доповідь з фактами. Заборонено підганяти рішення/правити тести.
## Обмеження
- один атомарний коміт; без нових залежностей; бюджет N хвилин
```

У DSH критерії приймання можна формалізувати: `workflow` з `opts.schema`
повертає валідований структурований звіт (`{status, commit, tests_output,
notes}`) замість вільного тексту — це заміна status-файлів зі старого
протоколу.

## 3. Мапінг старих механік на DSH

| Старе (hands.sh/qwen CLI) | У DSH |
|---|---|
| `hands.sh "тз"` | `subagent(prompt, run_in_background: true)` |
| `--continue` | `send_message` тому ж subagent_id (НЕ при паралельних) |
| `--name <slug>` | `description`/label агента; один slug = один виконавець |
| Логи `hands-logs/` | фінальне повідомлення жори + `job_output`; транскрипт живе в рантаймі |
| Cron-патруль + stall-детектор | НЕ ПОТРІБЕН: рантайм шле нотифікацію про settle; polling — антипатерн |
| PID-лок, зомбі-сесії | `list_agents` перед перезапуском; `interrupt_agent` для зупинки |
| Exit-гейт з pytest-хвостом | вимога в ТЗ: звіт = вивід команд (evidence, не assertion) |
| `hands_lessons.md` у хвості ТЗ | цей скіл + `notes/`-файли; рецидиви — через `/remember` |
| Квота qwen 429 | жори можуть їздити на іншій моделі: `workflow` `agent(prompt, {provider, model})` — голова на сильній моделі, руки на дешевій |

## 4. Верифікація — гейт, не довіра

- Після кожного жори голова ОСОБИСТО: `git diff` + конкретні тести з ТЗ.
  Звіт "passed" без гейта — не звіт.
- Той, хто робив, не оцінює себе сам: верифікація у голови або окремим
  свіжим агентом (adversarial review через workflow).
- Звіт жори = evidence: вивід команд, diff --stat, номери комітів.
  "Все працює" без виводу = повернути на доробку.

## 5. Паралельність

- Паралелимо ТІЛЬКИ незалежні файли. Дві задачі на один файл — не паралелимо,
  крапка (інцидент viz-v3: перезаписали верифікований результат).
- Без спільних mutable-ресурсів (кеші, stats-файли, один git-індекс на
  коміти) — або серіалізація через голову.
- Не більше 3 жор одночасно (емпірика: зомбі, merge-ризики).
- Зведений звіт по паралельних жорах — ТІЛЬКИ після завершення ВСІХ
  (у workflow для цього `parallel()` = бар'єр; не починати синтез раніше).
- Clean-tree перед запуском паралельних: `git status --porcelain` порожній,
  інакше rollback стає археологією.

## 6. Уроки жор (рецидиви — пам'ятати і вкладати в ТЗ за потреби)

1. **Зомбі/дублі**: перед перезапуском задачі — `list_agents`; живий
   попередник на тих самих файлах = стоп, не перезаписувати.
2. **Тиха недоступність інструментів**: якщо задача потребує веб/мережу —
   вимагай evidence (URL, вивід curl); "з пам'яті з виглядом повноцінного"
   — найгірший сценарій.
3. **Чекаючі задачі**: не сиди в циклі очікування — фонова job'а +
   нотифікація; жорі очікування не віддаємо.
4. **Тести — read-only**, якщо не в scope. Ніколи не прав тест під
   реалізацію; суперечність ТЗ↔тест = state=blocked з цитатами обох сторін.
5. **Коміт — тільки свої файли зі scope**: `git status` перед комітом;
   чуже незакомічене не чіпати і не включати.
6. **Windows-консоль ≠ твій shell**: кирилиця/емоджі в print падають у
   cp1251/cp866; CLI-інструменти — `sys.stdout.reconfigure(encoding="utf-8")`
   на старті. "Працює в моєму shell" ≠ "працює в користувача".
7. **Reasoning-моделі в API**: для JSON-відповідей DeepSeek — гасити
   thinking, інакше content порожній.
8. **Kill mid-write**: перед DISCARD незавершеної роботи — зберегти
   `git diff` у файл (іноді там 90% роботи).

## 7. Чого свідомо НЕ робимо

- Не будуємо cron-вотчери і LLM-патрулі — рантайм DSH подієвий.
- Не паралелимо >3 виконавців, не паралелимо спільні файли.
- Не делегуємо без повного ТЗ; не віримо звітам без evidence.
- Не даємо жорам грошові/деструктивні операції без явних параметрів і
  перевірки фактичного стану після (принцип 3, див. скіл work-conventions).
